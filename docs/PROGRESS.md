## 현재 상태 (2026-10-09)

- **목적:** Three.js 로 만드는 멀티플레이 게임 모음. 쯔꾸르(RPG Maker)식 로비에서 여러 명이 함께 돌아다니다가 문을 통해 각자 만든 게임으로 입장한다. 게임의 형식은 자유.
- **진행:** 하네스 적용 직후. 코드 없음. `verify.sh` 는 하네스 검사만 돈다 (앱 단계 미등록)
- **검증 기준선:** 하네스 검사 3단계 PASS (docs · reviewer model · script line endings). 앱 단계 숫자는 스택 결정 뒤 첫 초록 시점에 적는다
- **다음 작업:** 첫 `/next` 세션에서 「열린 질문」 1~3 을 사용자와 결정 → 그 결정대로 로비 스캐폴드(빈 Three.js 씬 + dev 서버) → `scripts/verify.sh` 에 typecheck/build 단계 등록 · `scripts/hooks/stop-verify.sh` 의 `CODE_PATHS` 를 실제 폴더로 · `.claude/settings.json` allow 에 러너 명령 추가
- **차단 요소:** 없음. 단, 스캐폴드는 열린 질문 1~3 의 결정이 선행

## 열린 질문 (다음 세션에서 사용자와 결정)

> `/next` 3단계가 보는 곳. 결정되면 결정 기록으로 옮기고 여기서 지운다.

1. **게임 입장 계약** — 로비가 게임을 어떻게 여는가.
   (a) 게임은 독립 페이지, 로비는 URL 로 이동(또는 iframe) — 게임 형식 완전 자유, 로비와 상태 공유 없음.
   (b) 게임이 `mount(container)` / `unmount()` 류 모듈 인터페이스를 구현하고 로비가 같은 페이지 안에서 띄움 — Three.js 인스턴스·플레이어 정보 공유 가능, 대신 게임이 이 계약을 따라야 함.
   "형식 자유" 에 가까운 쪽은 (a). 돌아오는 길(게임 → 로비, 결과 전달 여부)도 같이 정한다.
2. **멀티플레이 전송** — 로비에서 서로 보이려면 서버가 필요. WebSocket 서버 자체 운영(Node + ws / Socket.IO / Colyseus) vs WebRTC P2P(서버 최소, NAT 문제). 위치의 권위(서버가 정하는가, 클라이언트를 믿는가) · 호스팅 위치.
3. **저장소 구조·빌드** — 한 저장소에 `lobby/` + `games/<이름>/` + `server/`(모노레포·워크스페이스) vs 게임은 각자 저장소이고 로비는 링크만. 번들러(Three.js 의 사실상 표준은 Vite) · TypeScript 여부 · 패키지 매니저.
4. **로비 렌더링** — Three.js 직교 카메라 + 스프라이트(쯔꾸르 외형 그대로) vs 3D 로 재해석. 타일맵·캐릭터 에셋 출처(직접 제작 / 무료 에셋 — 라이선스 확인).
5. **협업 방식** — 원격 저장소 위치 · 브랜치 규칙 · 게임마다 담당자 1명인지. 원격이 생기면 `harness_default` 의 `parts/git-flow/` 가 후보.
